Free browser demo

No installation, API keys, GPU, or backend server required.

  1. Open Try Saylo.
  2. Keep Browser demo selected and choose a language.
  3. Select Start conversation. Type “Hello” or “What can I try in Saylo?” and select Send.
  4. For voice input, select Use microphone and grant permission. Select Read replies aloud for browser speech playback. If either feature is unavailable, continue by typing.
  5. Select End conversation to view a recap. Reopen a session under Recent conversations, copy its recap, or delete it.
What this demo does

It demonstrates voice input, a complete transcript, local conversation history, and extractive recaps. Its replies use simple local rules; they are not generated by a language model. It does not reproduce the original runtime’s adaptive speech recognition, free-form AI replies, or interruption handling.

Browser speech recognition may send audio to its vendor. Speech support and installed voices depend on your browser/device. Transcripts stay in this browser’s localStorage; blocked or full storage falls back to memory. No audio is saved by Saylo.

Run the free site locally

Install Node.js 20 or later, open a terminal in the Saylo project folder, then run: 

npm start

Open http://localhost:3000. No dependency installation is needed for the static demo.

To check and export the project:

npm test
npm run check
npm run build

The generated dist/ folder can be served at the root of an HTTPS static host. It contains no provider keys or API functions.

Self-hosted voice runtime

This is the complete provider-backed path: WebRTC audio → adaptive speech-to-text → your application agent → voice router → spoken audio. The runtime sends conversation events to your application, then turns its replies into speech.

Requirements

The default stack needs Linux with Docker Compose, an NVIDIA GPU available to Docker for the voice router, and Deepgram, Groq, and Sarvam credentials. AssemblyAI is optional. Provider usage and hardware can cost money. This runtime is not included in the free hosted demo.

  1. From the Saylo source folder, copy the environment template and add your provider keys locally. Never paste keys into the browser or commit them. 
cp .env.example .env
# Edit .env locally with your provider credentials.
docker compose up --build

The existing stack starts the voice server on :8080, the voice router on :8300, and the original quickstart page/agent on :8400/:9101.

  1. Run npm start for the Saylo frontend. Open http://localhost:3000/try.html and select Self-hosted voice runtime.
  2. Enter http://localhost:8080 as the server address and select Start conversation. Allow microphone access. The existing runtime’s events populate the same transcript and local history interface.
  3. For your own agent, set [agent] url in configs/saylo.toml. The contract has four request types: listen, greeting, chat, and oneshot. Keep the existing provider identifiers and config paths unchanged.

Restart the runtime after changing its config. The default endpoint on port 9101 belongs to the included quickstart agent; replace it with your application's address when integrating your own app. The default setup uses Deepgram, Groq and Sarvam; AssemblyAI is an optional fallback. Your application supplies any business data, model integration, booking logic and human handoff.

Remote calling needs a reachable HTTPS runtime and working ICE/NAT connectivity; configure TURN where needed. On a Mac, the default NVIDIA Docker reservation cannot use the Apple GPU. The router has a native CPU option; see native setup on a Mac. Apple GPU support is not part of the default container setup.

Connect your runtime
Mac / Apple Silicon: native setup

The default NVIDIA container configuration cannot use the M4 GPU. The router supports CPU execution. Use Python 3.11, a separate environment and the checked-in constraints. The first launch downloads model weights.

cd voice-router
python3.11 -m venv .venv
.venv/bin/python -m pip install torch==2.9.1
.venv/bin/python -m pip install -r requirements.txt -c constraints.txt
.venv/bin/python -m pip uninstall -y unidic
.venv/bin/python server.py --device cpu --port 8300 --voice female

If an audio/phonemizer dependency has no compatible Mac wheel, resolve that installation before proceeding. Do not replace pinned packages blindly.

With a working router, run the Go server natively from the project root in another terminal. Install Go 1.25+ first and keep provider credentials in your local environment file:

cp configs/saylo.toml config.toml
set -a
. ./.env
set +a
go run .

In a third terminal, from the project root, load the same environment and start the included call page and agent:

set -a
. ./.env
set +a
node quickstart/server.mjs

Open http://localhost:8400, or run npm start and connect through Saylo's self-hosted mode. Provider accounts are still required for the default recognition pipeline. Apple GPU/MPS execution is not preconfigured by these instructions.

Connect your application endpoint

Edit the existing [agent] section in configs/saylo.toml. Keep [llm] provider = "agent". The runtime calls your endpoint; the browser connects to the runtime, not directly to your app.

[agent]
url = "https://your-app.example.com/voice/agent"
timeout_ms = 60000

Set STREAMCORE_AGENT_API_KEY on the runtime and validate that same value in your app's Authorization: Bearer header. Keep the key on your servers. For containers, use an address reachable from the runtime's network; container loopback may not be your Mac's loopback.

Example turn

Saylo sends an HTTP POST with JSON:

{
  "session_id": "example-call",
  "type": "chat",
  "text": "What are your opening hours?",
  "language": "en"
}

Your application looks up the answer and returns JSON:

{
  "text": "[lang:en] The office is open from 9 AM to 5 PM."
}

Use your own business facts. Match the caller's language to one the voice router currently supports, and prefix each sentence with its [lang:xx] tag. Set end_call: true to finish after the spoken reply. The full contract also covers interrupted and replaced turns, session state, and streaming responses.

Included example application

The repository includes a fictional, English-only college enquiry endpoint. It uses local rules and needs no model key:

node demo-agent/server.mjs

Point your runtime's [agent] url at http://127.0.0.1:9102/agent when both processes share the host network. It handles all four events; ask about hours, documents or location. The original quickstart agent on port 9101 remains available for model-backed replies using your credentials.

The sample endpoint has HTTP integration tests. See the repository's demo-agent/README.md and docs/saylo/agent-contract.md for the event contract.

Connect telephone calls

Use your own Twilio account and number. Configure TWILIO_AUTH_TOKEN on the runtime and expose it through a reachable HTTPS/WSS address. The existing /twilio/media route accepts signed Twilio streams.

Configure your Twilio call flow to return this TwiML, using your actual runtime host and resource identifier:

<Response>
  <Connect>
    <Stream url="wss://your-runtime.example.com/twilio/media">
      <Parameter name="resource_id" value="your-caller-id" />
    </Stream>
  </Connect>
</Response>

If a reverse proxy rewrites the host, set SAYLO_TWILIO_STREAM_URL to the public stream URL used by Twilio. Phone calls, numbers and provider usage are billed to your accounts. SIP integration is available through the original sip-server path.

The static website does not host the telephone runtime. Run the runtime at the public stream URL above.

Troubleshooting

I can open the website but calls do not connect.
The static frontend and voice backend are separate. Start your runtime and enter its address on port 8080, not the call page on port 8400 or the voice router on port 8300.
The runtime cannot reach my application.
Check the endpoint URL from the runtime's machine/network, the bearer key and the JSON response. Restart after config changes. Inside a container, localhost may refer to the container rather than your host.
The caller is heard but no reply is spoken.
Check application responses and the router's GET /health. Use only the languages currently listed there, check provider credentials and balances, and inspect runtime logs locally.
My browser cannot reach the runtime.
A remote HTTPS page needs a reachable secure runtime. Check browser network permissions and ICE/NAT/TURN connectivity. For local development, use the localhost frontend with your localhost server.
Microphone input is unavailable.
The browser demo needs speech-recognition support and permission; typing remains available. A full runtime session uses WebRTC microphone capture and needs a secure context or localhost.
Twilio connects but audio or authentication fails.
Check the public WSS URL, TWILIO_AUTH_TOKEN, proxy host handling and signed stream requests. The backend must be publicly reachable; the static website alone cannot receive phone audio.

Before calling an integration verified

  1. Confirm a spoken question reaches your application endpoint.
  2. Hear its returned answer and check the transcript.
  3. Test interruption, ending/restarting, endpoint errors and unavailable speech providers.
  4. Reload and reopen the saved conversation. Test a telephone call separately if using Twilio.

Backend build and automated tests do not replace an actual provider-backed audio test. Record your environment and results before using it with real callers.
